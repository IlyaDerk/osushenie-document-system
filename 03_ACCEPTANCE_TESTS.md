# 15 сценариев приёмочного тестирования

Перед каждым сценарием использовать тестовую копию таблицы. Функция запуска:
`createMissingDocumentsForAllObjects`. Проверить, что выделенная строка не влияет
на результат и что модуль валидирует только шесть участвующих листов.

## 1. Первый запуск по новому объекту

При корректном объекте, восьми автоматических типах и отсутствии фактов создаются
восемь строк в порядке справочника с ID `DOC-{ID объекта}-0001` … `0008`.
Поля заполнены по спецификации. Создаётся одна успешная операция и история каждого
автоматически заполненного непустого поля; пустые поля в историю не попадают.

## 2. Повторный запуск

При существующем полном комплекте создаётся ноль строк, факты не меняются, операция
получает статус `Без изменений`, а история изменений не пополняется.

## 3. Один недостающий документ

Если из восьми типов отсутствует только `КС-3`, создаётся только он. Существующие
строки не меняются, ID продолжает последовательность максимальным номером плюс один.

## 4. Новый тип в справочнике

После добавления нового автоматического типа он создаётся для каждого корректного
объекта, где сочетания ещё нет; старые документы не дублируются.

## 5. Неполный объект

Объект без обязательного поля пропускается, остальные обрабатываются. В отчёте и
комментарии операции указаны строка, ID и причина; статус —
`Успешно с предупреждениями`.

Дополнительно проверить объект, у которого `ID объекта` содержит только обычные или
неразрывные пробелы, и объект, у которого другое обязательное текстовое поле содержит
только пробелы. Оба объекта пропускаются, документы для них не создаются, причина
содержит название незаполненного поля, а ID вида `DOC--0001` не возникает.

## 6. Пустая фактическая дата окончания

Объект корректен, документы создаются, фактическая дата остаётся пустой и строка
истории для этого поля не создаётся.

## 7. Ошибка дат

Для значения, которое не является настоящей датой, и для планового окончания раньше
начала соответствующий объект пропускается с точной причиной; остальные объекты
обрабатываются.

## 8. Повторяющийся ID объекта

Если ID встречается в нескольких строках, пропускаются все строки с этим ID,
документы для них не создаются, а все конфликтующие номера строк перечисляются.

## 9. Неполное автоматическое правило

При отсутствии ID или названия у строки с признаком `Автоматически` запуск
останавливается до записи фактов. Ошибка содержит лист, строку и поле. Выполняется
best-effort запись операции со статусом `Ошибка`, не подменяющая исходную ошибку.

## 10. Дубли правил

Проверить три варианта: повтор ID с разными названиями, две полностью одинаковые
автоматические строки и одно название с разными ID. Каждый вариант критичен и
останавливает операцию до записи документов.

## 11. Дубль сочетания объект/тип

При двух существующих строках с одинаковым ключом третья не создаётся, существующие
не меняются, один различный дублирующийся ключ отражается в предупреждениях и статусе
`Успешно с предупреждениями`.

## 12. Неполная строка фактов

Строка без `ID объекта` или `ID типа документа` не участвует в комплектности и не
блокирует создание корректного документа. Она учитывается в предупреждениях.
Архивные и удалённые строки с полным ключом, напротив, блокируют повторное создание.

## 13. Продолжение нумерации

При `DOC-2605-0001`, `DOC-2605-0002`, `DOC-2605-0005` следующий ID —
`DOC-2605-0006`. Пропуск не переиспользуется. Нестандартные старые ID не меняются,
а глобально занятый кандидат пропускается.

## 14. Одновременный запуск и изолированная структура

Два почти одновременных запуска выполняются последовательно под общей блокировкой,
без дублей ключей и ID. Ошибка структуры одного из шести участвующих листов блокирует
операцию. Ошибка только в `OPERATOR_CARD`, `EMPLOYEES` или `CLIENTS` не блокирует её.
Отсутствие обязательного значения в `CARD_DICTIONARY` является критической ошибкой.

## 15. Истории и частичный технический сбой

После создания проверить одну строку `История операций` с общим `OP-YYYYMMDD-NNNN`, временем,
email, источником, типом, статусом и согласованными счётчиками. Каждая строка
`История изменений` имеет уникальный `CHG-YYYYMMDD-NNNN-MMMM`, тот же ID операции, действие
`Создание`, пустое старое значение, отображаемое новое значение и фактический номер
строки документа.

Имитировать ошибку записи истории изменений после записи фактов. Документы остаются,
откат не выполняется, операция по возможности получает статус `Ошибка`, пользователь
видит сообщение `Документы созданы, но запись истории изменений завершилась ошибкой`
и фактическое количество созданных документов. Сбой best-effort журналирования не
заменяет исходную ошибку.

# Общий критерий приёмки

- пройдены все 15 сценариев;
- повторный запуск не создаёт дубли;
- ошибка одного объекта не блокирует остальные;
- критическая ошибка до записи не допускает создания;
- архивные и удалённые строки учитываются по полному ключу;
- код не зависит от букв и порядка столбцов;
- факты и истории записываются пакетно без `appendRow` в циклах;
- `Code.gs`, `OperatorSidebar.html`, `onOpen` и архитектура карточки не изменены.

## Результат ручной приёмки базовой версии

Все перечисленные выше 15 сценариев массового создания вручную выполнены и успешно
пройдены в реальной Google Sheets / Apps Script до начала пакета синхронизации.

## Автоматизированные проверки пакета синхронизации

Мок-набор `tests/run-tests.js` проверяет 20 исходных требований и две регрессионные
проверки ревью: читаемые и последовательные
ID, поиск по обеим историям и совместимость со старыми UUID; связь ID изменений с
операцией; отсутствие изменений при равных данных; массовое обновление активных строк;
очистку пустым источником; неизменность даты статуса документа; некорректные даты и
дубли объектов; старые/новые значения истории; HTML критической ошибки; только два
обязательных значения справочника; сохранение фактов при сбое истории; неизменность
`Code.gs`, `OperatorSidebar.html` и `onOpen`.
Дополнительные проверки подтверждают, что пакетная запись синхронизации не затрагивает
несинхронизируемые значения и формулы, а административная функция не ослабляет чужие
защиты и повторно использует только собственную warning-only protection.

Дополнительно в реальной таблице необходимо проверить права warning-only protection,
email активного пользователя, визуальный вид HTML-диалога и два действительно
одновременных кнопочных запуска: Node-моки не воспроизводят инфраструктуру Google.

## Дополнительные регрессионные проверки PR №2 по объёму истории

- Создание документа теперь фиксирует одну логическую запись истории на документ с полем «Создание документа» и многострочным первоначальным снимком вместо отдельной записи на каждое заполненное поле.
- Массовое создание 18 документов должно давать 18 строк «История изменений» и значение «Полей изменено» = 18.
- Синхронизация объектных данных продолжает обновлять «Дата обновления» и «Кто обновил (email)» в фактах, но не создаёт по ним отдельные строки истории; счётчик «Полей изменено» считает только бизнес-поля.
- Ручная архивация истории изменений проверяется отдельно: дата отсечения, группировка по месяцам, дедупликация по «ID изменения», запрет удаления рабочих строк до проверки архива, критические ошибки на пустых и повторяющихся ID.

## Карточка операциониста — ручная приёмка чтения

Актуальные шесть сценариев чтения (программное «Все»/пустой объект, конкретный объект, комбинированные фильтры, включительные даты, нулевая выдача и дубли с повторной загрузкой) приведены в разделе «Ручная приёмка» файла `05_OPERATOR_CARD_READ_SPEC.md`. Они выполняются на копии рабочей Google-таблицы и не заменяются Node mock-тестами.

Дополнительно при ручной приёмке проверить реальные объекты после программного `Все`, временный список прорабов по должности `Экспедитор`, статусы из `Справочник для КО`, локальную кнопку `Очистить фильтры` и семь data validations карточки. После обычной, нулевой и повторной загрузки dropdown должны сохраняться, включая карточку со смещённым рабочим блоком.

## Save-stage карточки

Проверить сценарии A–Q из `06_OPERATOR_CARD_SAVE_SPEC.md`, all-or-nothing pre-write validation, optimistic conflict, employee/client holder, очистку технических ID, duplicate resolution по физическим строкам и отсутствие второй load-operation после refresh.
