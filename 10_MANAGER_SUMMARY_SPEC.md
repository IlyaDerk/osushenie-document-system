# Сводная руководителя

## Назначение и источники

`rebuildManagerSummary()` формирует generated/read-only лист **Сводная руководителя**. Единственные источники — централизованные листы `OBJECTS`, `DOCUMENTS` и `CARD_DICTIONARY` из `SystemCore.gs`. Они читаются одним snapshot и не изменяются. Каноническая модель `objectCardBuildModel_()` обеспечивает active-only, группировку по объекту, orphan, динамические статусы, natural sort и полный учёт.

## KPI

Общее состояние содержит количество всех объектов, проблемных объектов, объектов без документов, активных документов, подписанных, неподписанных, требующих исправления, готовность и orphan. Готовность равна доле статуса **Подписан с обеих сторон**, либо 0% при отсутствии документов. Полностью готов только объект хотя бы с одним активным документом, у которого подписаны все активные документы; остальные реальные объекты проблемные.

Распределение статусов непосредственно копирует порядок и числа канонической модели Карточки объектов: справочник, неизвестные фактические статусы в natural order, затем единственная колонка **Без статуса**.

## Сроки

Сроки считаются только у активных неподписанных документов как календарные дни timezone таблицы. Просрочка — дата раньше сегодня; ближайшие 14 дней — включительно от сегодня до сегодня + 14; пустая дата — отдельный bucket. Дата после горизонта не входит в bucket. Подписанный документ исключён из всех deadline KPI. Непустая невалидная дата прерывает rebuild до публикации. Ближайший срок — минимальная валидная дата неподписанного документа.

## Контроль и сортировка

Единственный сценарий выбирается по приоритету: **Просрочено**, **Требует исправления**, **Срок сегодня**, **Срок до 14 дней**, **Без плановой даты**, **Нет документов**, **Не завершено**. Проблемные объекты сортируются по этому приоритету, затем по ближайшей дате (пустые последние), затем natural sort ID.

## Orphan

Активный документ с пустым/неизвестным ID объекта включается во все глобальные документные KPI, статусы, сроки и готовность. При наличии orphan внизу проблемной таблицы выводится отдельная строка **⚠ Документы без найденного объекта**. Она не увеличивает KPI проблемных объектов.

## Инварианты

До очистки generated-листа проверяются: равенство глобального total сумме статусов и назначений объект/orphan; signed + unsigned; классификация каждого объекта ровно как готового или проблемного; уникальность проблемных объектов; непересечение deadline buckets; совпадение итогов с моделью Карточки объектов. Источники остаются read-only.

## Rebuild и trigger

Полный цикл validate → batch read → canonical model → management model → invariants → batch publish выполняется внутри одного document lock. Формулы, графики, уведомления и автоматические triggers отсутствуют. После приёмки владелец может вручную создать time-driven trigger для `rebuildManagerSummary()`; код сам trigger не создаёт.
