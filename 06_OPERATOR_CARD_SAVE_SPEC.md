# Сохранение карточки операциониста

## Контракт и подготовка к deployment

Пользователь уже подготовил рабочий блок листа «Карточка операциониста»: первые 25 заголовков соответствуют факту, **26 — `Статус записи`**, **27 — `Номер строки в таблице фактов`**. Код не создаёт и не перестраивает колонки; он строго проверяет их наличие. Колонки `ID документа`, `ID объекта` и 27 технические и скрывается loader-ом. В `Справочник для КО` в колонке `Статус записи` вручную должны присутствовать `Активная`, `Архивная`, `Удалённая`.

Первые 25 полей и их порядок совпадают с `Документы объектов`. `Название объекта` — обычное синхронизируемое read-only поле факта; скрытые ID остаются ключами identity/optimistic concurrency. `Объекты` остаётся источником истины для `Номер договора`; `SyncObjectData.gs` переносит его в активные документы, поэтому карточка показывает, но **не сохраняет** это поле и не изменяет лист `Объекты`.

## Workflow

`saveOperatorCardChanges` передаёт работу в `OperatorCardSave.gs`. **Partial save is the business rule**: ошибка одной строки не лишает оператора возможности сохранить корректную часть работы.

Под `withDocumentLock_()` до первой записи проверяются все глобальные зависимости: `DOCUMENTS`, `OPERATOR_CARD`, `CARD_DICTIONARY`, `EMPLOYEES`, `CLIENTS`, `CHANGE_HISTORY`, `OPERATION_HISTORY`, их заголовки и системная конфигурация. Ошибка этого уровня фатальна и не меняет факты. `generateOperationId_()` также вызывается только внутри lock.
Ошибка внутри fact write также global/fatal: завершённой запись считается только после успешного завершения всех batch writes. При сбое результат считается неопределённым: часть batch ranges могла быть записана, rollback не обещается, success не возвращается, а оператор должен повторно загрузить карточку до продолжения работы.

Ошибки physical row, identity, optimistic `Дата обновления`, read-only поля, типа, справочника, holder/transfer, перехода статуса и duplicate-group являются row/group-level. Они попадают в `rowErrors` / `groupErrors`; rejected rows не попадают ни в fact write-plan, ни в `История изменений`. Неизменённая строка не требует write и не становится ошибкой только из-за stale version.

При full success запускается обычный refresh без второй load-operation. При partial success полного refresh нет: rejected card rows и введённые в них значения остаются неизменными, а у успешных card rows точечно обновляются `Дата обновления` и email. Это не даёт уже сохранённым строкам ложный stale conflict при повторном save.

`У кого документ` использует единый список: сотрудники, затем клиенты, labels `Название [ID]`; в факте сохраняются чистое имя и ST/CL ID раздельно. `Кто передал` допускает только сотрудника. Очистка label очищает ID.

`Дата начала работ`, `Дата окончания (по плану)` и `Дата окончания (по факту)` копируются из объекта только при создании документа. Затем они редактируются в карточке и сохраняются как пустое значение или корректный `Date`; `SyncObjectData.gs` их больше не перезаписывает.

При повторном открытии Sidebar сервер проверяет наличие в карточке строки с непустым `ID документа`, целым физическим `Номер строки в таблице фактов` и совпадающим ID в указанной строке фактов. Только в этом случае кнопка `Внести изменения` активируется без повторного применения фильтров и без перезагрузки карточки. `Очистить фильтры` не сбрасывает это состояние.

`Статус записи` берётся из `Справочник для КО`. Для загруженной активной строки разрешены только `Активная`, `Архивная`, `Удалённая`. Архивация/удаление не совмещаются с business edits. Для затронутого дубля карточка обязана содержать все активные физические строки; допускается только status resolution с итогом не более одной активной строки. Partial/unresolved group отклоняется как единая группа, но не мешает другим документам. Дубли, которые save не затрагивает, не влияют на операцию.

История изменений содержит пользовательские business changes, изменения holder/transfer ID и статуса записи, но не производные `Дата обновления`, email и дату смены статуса документа. История операций содержит одну строку и существующие счётчики.

## Ручной acceptance

A. Изменить комментарий.  
B. Изменить статус документа и проверить дату смены статуса.  
C. Выбрать сотрудника-держателя.  
D. Выбрать клиента-держателя.  
E. Выбрать «Кто передал».  
F. Очистить держателя и проверить очистку ID.  
G. Изменить числовую сумму.  
H. Повторить save без изменений.  
I. Изменить факт извне и проверить stale `Дата обновления`.  
J. Уникальную строку перевести в `Архивная`.  
K. Уникальную строку перевести в `Удалённая`.  
L. Из двух активных дублей одну перевести в `Удалённая`.  
M. Из двух активных дублей одну перевести в `Архивная`.  
N. Отфильтровать часть duplicate group и проверить блокировку.  
O. Проверить исчезновение archive/delete после reload.  
P. Проверить строки `История изменений`.  
Q. Проверить единственную строку `История операций`.

## Backlog

Отдельный режим **«Разобрать дубли»** должен находить группы, показывать физические строки рядом и позволять оставить активной, архивировать, удалить, а после отдельного согласования — присвоить новый ID действительно иному документу. Отдельный UI сейчас не создаётся; `Статус записи` — временный MVP.

## UX-защита read-only полей

В проекте существует один простой `onEdit(event)`, который маршрутизирует событие во внутренние обработчики листа `Объекты` и карточки. `operatorCardHandleReadOnlyEdit_()` реагирует только на ручные изменения строк данных `Карточка операциониста` и определяет read-only столбцы исключительно через `SYSTEM_CONFIG.CARD_FIELD_MAP` (`editable === false`). Программные записи loader через `setValues()` простой trigger не запускают; protection диапазонов не используется.

Для каждой затронутой строки обработчик читает технический `Номер строки в таблице фактов`, пакетно получает требуемый диапазон `Документы объектов` и проверяет `ID документа`, `ID объекта`, `ID типа документа`. При корректной identity изменённые read-only ячейки восстанавливаются из факта и получают note `Поле заполняется автоматически и недоступно для ручного изменения.` Editable-ячейки того же paste не перезаписываются. При неверной физической строке или identity значение из другой строки не подставляется, а на ячейке остаётся диагностический note с предложением обновить карточку. Отклонённая попытка не журналируется. Серверная read-only проверка `OperatorCardSave.gs` остаётся обязательным вторым уровнем защиты.
