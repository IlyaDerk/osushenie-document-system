# Чтение «Карточки операциониста»

## Назначение и архитектура

Первый рабочий этап карточки только читает данные. `Code.gs` содержит публичные endpoint-функции, `OperatorCard.gs` выполняет серверную проверку, чтение и запись, а `OperatorSidebar.html` отвечает за UX. Единственный источник строк — `Документы объектов`; `Объекты` и справочники читаются только для фильтров и проверки ID. Конфигурация листов, заголовков, значений и блокировки берётся из `SystemCore.gs`.

Весь запуск `applyOperatorFilters` выполняется под `withDocumentLock_`: повторно читаются справочники, проверяются ID и структура, затем читаются факты, формируется результат, заменяется карточка и добавляется одна операция.

## Фильтры

Фильтры объединяются по И: объект (`ID объекта`), прораб (`ID ответственного прораба`), нормализованный статус документа, тип (`ID типа документа`), держатель (`ID сотрудника — у кого документ`) и диапазон по `Дата создания`. Выбор из справочников передаёт ID, поэтому одинаковые подписи не создают неоднозначности. Сервер не доверяет Sidebar и проверяет ID по актуальным справочникам.

Список объектов пакетно читается с листа `Объекты` по системным заголовкам `ID объекта` и `Название`. Чтение привязано к фактическим колонкам этих заголовков, а не к физической колонке A. Программное `Все` добавляется перед всеми естественно отсортированными реальными объектами. Для текущего этапа тестирования список «Ответственный прораб» временно отбирает сотрудников с нормализованной должностью `Экспедитор`; значение хранится централизованно в `SYSTEM_CONFIG.VALUES.FOREMAN_POSITION`, а фильтрация фактов остаётся по `ID ответственного прораба`.

Статусы документов Sidebar читаются из системного листа `CARD_DICTIONARY` (`Справочник для КО`), колонка `Статус документа`. Пустые значения и нормализованные дубли удаляются, а `Все` добавляется программно первым. Сервер принимает только пустое/`Все` или актуальное значение этого справочника.

В Sidebar даты визуально объединены общим заголовком `Дата создания` и подписями `От`/`До`; серверный контракт `dateFrom`/`dateTo` и алгоритм часового пояса не изменены. Состояние `Все` у пяти справочных фильтров показывается серым `placeholder`, при этом фактическое значение input остаётся пустым, а системное `Все` не добавляется в datalist. Кнопка `Очистить фильтры` локально очищает пять фильтров, обе даты и области сообщений, не вызывает сервер, не очищает карточку и не создаёт операцию. Пустые значения сохраняют прежнюю серверную семантику «фильтр не применяется».

### Программное «Все» и пустой объект

Первый элемент объектов `{id: "", name: "Все", isAllObjects: true}` создаётся кодом и не требуется в таблице. Реальные объекты сортируются после него. Реальный объект с нормализованным названием «Все» является ошибкой. Отсутствующий или очищенный объект, имя «Все» и `allObjects: true` означают все объекты. Конкретный режим требует существующий ID.

### Даты

HTML передаёт `YYYY-MM-DD`. Начала календарных дней вычисляются через `Utilities.parseDate` в `spreadsheet.getSpreadsheetTimeZone()`. Верхняя граница задаётся началом следующего календарного дня и сравнивается строго (`date < toExclusive`), поэтому границы включительны и DST учитывается. Пустая дата при активном диапазоне исключается; некорректная непустая дата исключается с warning.

## Активные строки, сортировка и дубли

Полностью пустые строки пропускаются. В выборку входят только строки со статусом записи `Активная` после нормализации пробелов/NBSP и регистра. Сортировка стабильна: `ID объекта`, `ID типа документа`, `ID документа`, физическая строка; строки сравниваются естественно с числовыми частями.

Карта дублей непустого `ID документа` строится среди всех активных строк до фильтров. Все прошедшие строки сохраняются. Если в выдачу попала часть дубля, warning перечисляет всю активную группу физических строк, а счётчик отражает число различных ID. Архивные аналоги не учитываются.

## Проверка и безопасная замена карточки

Перед записью стартовые колонки фактов и карточки независимо определяются по `headerMap` заголовка `ID документа`. Начиная с каждой найденной колонки строго проверяются 24 последовательных рабочих заголовка: NBSP/пробелы нормализуются, регистр — нет. Пустые или служебные колонки слева игнорируются, пустые колонки справа допустимы, но дополнительный непустой заголовок справа от рабочего блока карточки считается нарушением структуры. Ошибка сообщает лист, позицию, ожидаемое и фактическое значение и сохраняет старую выдачу. После проверки из строки фактов берутся 24 значения начиная с фактической колонки `ID документа`, без преобразования типов.

Старая выдача определяется по фактической колонке `ID документа` карточки с шестой строки. Один прямоугольник `max(oldRowCount, newRowCount) × 24` содержит новый результат и пустой хвост и записывается одним `setValues()` начиная с найденной стартовой колонки карточки. Форматирование, validations, строки, а также колонки слева и справа от рабочего блока не затрагиваются. Нулевая выдача тем же способом очищает старые значения.

## Журналирование и ошибки

Один запуск добавляет одну строку в `История операций` с типом `Загрузка карточки операциониста`, источником `Карточка операциониста`, временем, пользователем, реальными счётчиками, фильтрами и warnings. Счётчики изменений равны нулю. `История изменений` не вызывается. До записи карточки критическая ошибка сохраняет старую выдачу и журналируется best-effort. Ошибка журнала после успешной записи не откатывает карточку и возвращается как предупреждение.

## Выпадающие списки карточки

Перед пакетной заменой значений модуль идемпотентно применяет data validation ко всем подготовленным строкам карточки от `dataStartRow` до `getMaxRows()`. Физические колонки определяются только через `headerMap`, поэтому смещённый рабочий блок поддерживается. Правила создаются диапазонами по одному на колонку, не меняют оформление и сохраняются при обычной, повторной и нулевой загрузке, поскольку `setValues()` заменяет только значения.

Все варианты читаются из существующих справочников, без hardcode:

- `Статус документа` ← `Справочник для КО / Статус документа`;
- `Оригинал / ЭДО` ← `Справочник для КО / Оригинал / ЭДО`;
- `У кого документ` ← сначала `Справочник сотрудников / ФИО сотрудника`, затем `Справочник клиентов / Наименование клиента`;
- `Где документ` ← `Справочник для КО / Где документ`;
- `Кто передал` ← `Справочник сотрудников / ФИО сотрудника`;
- `Оплачен` ← `Справочник для КО / Оплачен`;
- `ГУ (Да/Нет)` ← `Справочник для КО / ГУ (Да/Нет)`.

Эти validations обеспечивают только UI выбора. Сохранение карточки обратно в факты и новая модель клиентских ID не входят в этап.

## Ограничения

Этап не сохраняет карточку обратно, не меняет факты/объекты/справочники, не создаёт документы, не использует Drive, API, уведомления и триггеры. Известная проблема `setupSystemDictionaryGuards()` не затрагивалась.

## Автоматические тесты

`node tests/run-tests.js` покрывает нормализацию и проверку фильтров, программное «Все», конфликт имени, даты/DST, active filtering, строгие заголовки, 24 поля, естественную сортировку, дубли, один batch-write, очистку хвоста и нулевой выдачи, запрет записи в факты/историю изменений, а также регрессию создания, синхронизации и архивации.

## Ручная приёмка

1. Открыть Sidebar: применить «Все», затем очистить объект и повторить; выдачи должны охватывать все объекты.
2. Выбрать конкретный объект без других фильтров; проверить фильтрацию по ID.
3. Для всех объектов одновременно выбрать прораба, тип, держателя и статус.
4. Подготовить даты на нижней, внутренней, верхней и внешней границе диапазона.
5. Получить нулевую выдачу; проверить очистку значений при сохранении оформления и validations.
6. Подготовить активный дубль и архивный аналог; проверить warning, обе активные строки и безопасную повторную загрузку.
