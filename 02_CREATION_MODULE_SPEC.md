# Спецификация модуля создания документов по объектам

## Цель

Реализовать Apps Script-модуль, который по нажатию кнопки `Создать документы` массово проверяет все объекты и добавляет в `Документы объектов` только недостающие документы, предусмотренные `Справочник документов`.

Главная функция:

```javascript
createMissingDocumentsForAllObjects
```

Пользователь не выбирает строку объекта. Один запуск обрабатывает весь лист `Объекты`.

## 1. Отбор объектов

Скрипт читает все строки `Объекты`, начиная со строки 4.

Корректный объект должен иметь:

- `ID объекта`
- `Название`
- `Номер договора`
- `ID ответственного прораба`
- `Ответственный прораб`
- `Статус объекта`
- `Дата начала работ`
- `Дата окончания (по плану)`

Необязательны:

- `Адрес`
- `Дата окончания (по факту)`

Проверки:

- `ID объекта` не повторяется;
- даты начала и планового окончания являются настоящими датами;
- плановое окончание не раньше начала;
- полностью пустые строки игнорируются;
- некорректный объект пропускается, остальные обрабатываются;
- при дубле `ID объекта` пропускаются все строки с этим ID.

## 2. Правила создания

Скрипт читает `Справочник документов`, начиная со строки 5.

В комплект включаются только строки:

`Создавать при создании объекта = Автоматически`

Сравнение допускается без учёта регистра и лишних пробелов.

Обязательны:

- `ID типа документа`
- `Тип документа`

Весь запуск останавливается до записи, если:

- отсутствует ID или название у автоматического правила;
- один ID типа повторяется;
- одно название связано с разными ID;
- нет ни одного правила автоматического создания.

Поля `Обязательность`, `Срок на исполнение от даты создания` и `Повторяемость` пока не влияют на первоначальное создание.

Порядок создания совпадает с порядком строк справочника.

## 3. Проверка существования

Ключ:

`ID объекта + ID типа документа`

Документ считается существующим независимо от:

- `Статус документа`;
- `Статус записи`;
- `Источник создания`;
- заполненности остальных полей.

Создаются только отсутствующие сочетания.

Если сочетание уже продублировано:

- новый документ не создаётся;
- существующие строки не меняются;
- дубль отражается в предупреждениях.

Строка без `ID объекта` или `ID типа документа`:

- не участвует в сравнении;
- не блокирует создание;
- учитывается как предупреждение;
- автоматически не исправляется.

## 4. Поля новой строки

Автоматически заполняются:

| Поле | Источник / значение |
|---|---|
| `ID документа` | Формируется скриптом |
| `ID объекта` | `Объекты → ID объекта` |
| `Тип документа` | `Справочник документов → Тип документа` |
| `Номер договора` | `Объекты → Номер договора` |
| `Статус документа` | `Ожидает заполнения` |
| `Статус объекта` | `Объекты → Статус объекта` |
| `Дата начала работ` | `Объекты → Дата начала работ` |
| `Дата окончания (по плану)` | `Объекты → Дата окончания (по плану)` |
| `Дата окончания (по факту)` | Копируется, если заполнена |
| `Дата создания` | Текущая дата и время |
| `Дата обновления` | Равна дате создания |
| `ID типа документа` | `Справочник документов → ID типа документа` |
| `Кто обновил (email)` | Email запустившего пользователя |
| `Ответственный прораб` | `Объекты → Ответственный прораб` |
| `ID ответственного прораба` | `Объекты → ID ответственного прораба` |
| `Дата изменения статуса документа` | Текущая дата и время |
| `Источник создания` | `Создание документов по объекту` |
| `Статус записи` | `Активная` |

Остаются пустыми:

- `Дата документа`
- `Оригинал / ЭДО`
- `Комментарий`
- `У кого документ`
- `Где документ`
- `Кто передал`
- `Оплачен`
- `Сумма документа`
- `ГУ (Да/Нет)`
- `Условия ГУ`
- `ID сотрудника — у кого документ`
- `ID сотрудника — кто передал`
- `Отчётный период`

Записываются значения, не формулы. Новые строки добавляются в конец таблицы фактов.

## 5. ID документа

Формат:

`DOC-{ID объекта}-{порядковый номер}`

Примеры:

- `DOC-2605-0001`
- `DOC-2605-0002`
- `DOC-OBJ-0021-0001`

Правила:

- общая нумерация внутри объекта;
- максимальный существующий номер + 1;
- пропущенные номера не переиспользуются;
- глобальная уникальность проверяется перед записью;
- ID не меняется после создания;
- старые нестандартные ID не переписываются;
- создание выполняется под блокировкой.

## 6. Ошибки и предупреждения

Критические ошибки, останавливающие весь запуск:

- отсутствует лист;
- отсутствует или продублирован обязательный заголовок;
- нет корректных автоматических правил;
- ошибка или дубль в справочнике;
- отсутствует статус `Ожидает заполнения`;
- не получена блокировка;
- техническая ошибка чтения или записи.

Ошибки объекта — пропустить объект:

- отсутствует обязательное поле;
- некорректная дата;
- плановое окончание раньше начала;
- дублирующийся `ID объекта`.

Предупреждения — продолжить:

- дубли сочетания объект/тип;
- дубли `ID документа`;
- строки факта с неполным ключом.

## 7. Истории и результат

Создание выполняется под блокировкой из `SystemCore.gs`.

После успешной записи:

- одна строка — в `История операций`;
- изменения созданных документов — в `История изменений`;
- все записи связаны одним `ID операции`.

Статусы:

- `Успешно`
- `Успешно с предупреждениями`
- `Без изменений`
- `Ошибка`

Итог пользователю содержит:

- проверено объектов;
- корректных объектов;
- пропущено объектов;
- правил создания;
- документов уже существовало;
- документов создано;
- дублей объект/тип;
- дублей `ID документа`;
- строк с неполным ключом;
- время выполнения;
- причины пропусков и предупреждения.

## 8. Технические требования

- Использовать `SYSTEM_HEADERS`, `H`, `SYSTEM_CONFIG` и функции `SystemCore.gs`.
- В начале запускать проверку структуры.
- Не создавать второй независимый справочник заголовков.
- Искать столбцы только по заголовкам.
- Не использовать буквы столбцов.
- Читать и записывать массивами.
- Новые строки записывать пакетно через `setValues`.
- Не использовать `appendRow` в циклах.
- Не менять существующие документы.
- Не исправлять дубли автоматически.
- Не подключать внешние API.
- Не менять `onOpen`, карточку операциониста и существующую логику сохранения.

## 9. Согласованные технические решения

### 9.1. Изолированная проверка структуры

Модуль не вызывает `assertSystemStructure_()`. Внутри общей блокировки он вызывает
`assertSystemSheetsStructure_(sheetKeys)` только для ключей:

- `OBJECTS`;
- `DOCUMENT_TYPES`;
- `DOCUMENTS`;
- `CARD_DICTIONARY`;
- `OPERATION_HISTORY`;
- `CHANGE_HISTORY`.

Ошибки структуры `OPERATOR_CARD`, `EMPLOYEES` и `CLIENTS` не останавливают создание.
Полная ручная проверка `validateSystemStructure()` остаётся без изменений.

Дополнительно до чтения объектов проверяется наличие в `CARD_DICTIONARY` значений
`Ожидает заполнения` в поле `Статус документа` и `Активная` в поле `Статус записи`.

### 9.2. Системные значения и технические ID

Все управляющие значения берутся из `SYSTEM_CONFIG.VALUES`, включая признак
`Автоматически`, четыре статуса операции, тип операции создания и действие
`Создание`. Источник операции и изменения — существующее значение
`OBJECT_CREATION_SOURCE`.

`ID операции` формируется функцией `generateOperationId_()` как `OP-` плюс UUID,
а `ID изменения` — функцией `generateChangeId_()` как `CHG-` плюс UUID.
Формат `ID документа` не меняется.

### 9.3. Статусы операции

- `Успешно`: создан хотя бы один документ, предупреждений нет.
- `Успешно с предупреждениями`: операция завершена, но есть пропущенные объекты,
  дубли, неполные ключи или иные предупреждения; документов может быть создано ноль.
- `Без изменений`: ничего не создано, предупреждений нет, комплект уже существует.
- `Ошибка`: критическая ошибка либо документы созданы, но обязательная история не записана.

### 9.4. Истории и ошибки

`ID операции` и время начала формируются до входа в блокировку. При критической
ошибке выполняется best-effort запись одной строки `История операций`; сбой этой
попытки не заменяет исходную ошибку.

После пакетной записи фактов в `История изменений` пакетно добавляется по одной
строке на каждое автоматически заполненное непустое поле. Пустые операционные поля
и пустая фактическая дата не журналируются. Старое значение пустое, действие —
`Создание`, источник — `OBJECT_CREATION_SOURCE`, номер строки — фактическая строка
нового документа. Даты объекта отображаются как `dd.MM.yyyy`, системные дата и время —
как `dd.MM.yyyy HH:mm:ss`.

Если факты созданы, но история изменений не записана, факты не удаляются, откат не
выполняется, статус операции — `Ошибка`, а отчёт содержит сообщение
`Документы созданы, но запись истории изменений завершилась ошибкой` и фактическое
количество созданных документов.

В `История операций` для этого модуля записываются: загрузка в карточку — `0`,
документы с изменениями и обновлённые строки факта — количество созданных документов,
изменённые поля — количество записанных строк истории изменений, дублирующиеся ID —
количество различных повторяющихся `ID документа`, ошибки — `0` либо `1`.
Поле комментария и пользовательский отчёт содержат все согласованные счётчики,
причины пропусков, предупреждения и критическую ошибку.

## 10. Утверждённая базовая версия и читаемые ID

Все 15 сценариев из `03_ACCEPTANCE_TESTS.md` вручную пройдены в реальной Google
Sheets / Apps Script; массовое создание считается утверждённой базовой версией.
Новые операции получают ID `OP-YYYYMMDD-NNNN`, а их изменения —
`CHG-YYYYMMDD-NNNN-MMMM`. Резервирование номера выполняется внутри общей блокировки,
с проверкой обеих историй. Старые UUID сохраняются и игнорируются при поиске максимума.
Служебный дневной максимум в Document Properties предотвращает повторное использование
последнего номера после ручного удаления строк истории.

Критические ошибки создания показываются через экранированный HTML-диалог с заметным
блоком `КРИТИЧЕСКАЯ ОШИБКА`; успешные результаты и предупреждения остаются текстовыми.
Справочник карточки проверяется только на системные значения `Ожидает заполнения` и
`Активная`; остальные пользовательские варианты свободно настраиваются.

## Уточнение по объёму истории изменений

Для каждого созданного документа модуль записывает одну логическую строку «История изменений»: тип действия «Создание», название поля «Создание документа», пустое старое значение и компактный многострочный первоначальный снимок непустых основных полей документа в «Новое значение». Счётчик «Полей изменено» при создании равен количеству созданных документов и строк истории создания.
